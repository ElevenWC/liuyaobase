## 4. 内部逻辑要点

### 4.1 建表（v0.0）
- 按依赖关系倒序 DROP（子表先删），再按正序 CREATE
- 建表 SQL 来自 `.A1数据库设计.md` §六完整 SQL
- 共 16 张表 + 36 个索引
- 执行顺序：DROP 全部 → CREATE 全部 → CREATE INDEX

### 4.2 填充 bagong_gua（v0.0，64 条）
- 数据来源：`.user/zhouyiData.json` → `basic` 数组
- 每条：code、name、palace、element、palace_type
- 直接读取 JSON → 批量 `session.add_all()` → `commit()`

### 4.3 填充 guaci（v0.0，64 条）
- 数据来源：`.user/zhouyiData.json` → `content` 数组
- 每条：code、gua_ci、tuan_zhuan、xiang_zhuan、yao_ci(JSON)、wenyan、yong
- yao_ci 和 yong 是 JSON 类型 → `json.dumps()` 序列化
- 乾坤文言中的 `|` 保持原样存入

### 4.4 填充 system_config（v0.0，1 条）
- `INSERT INTO system_config VALUES ('last_import_time', '')`

### 4.5 注册存储函数（v0.0，8 个）
- 读取 `backend/db/stored_functions/*.sql`
- 逐条 `DROP FUNCTION IF EXISTS` → `CREATE FUNCTION`
- 顺序：先生克合冲 → 后半合三合 → 后生旺墓绝 → 后八宫关系

### 4.6 回填 static_* 数据（v0.1 新增）
⚠️ 此部分在 v0.1 核心算法完成后添加，v0.0 不实现。

- `seed_static_data(session)` 调用：
  - `najia.get_yao_info(code)` → static_gua_yao_info（384 条）
  - `fushen_zengshan.get_fushen(code)` → static_fushen_zengshan（~64 条）
  - `fushen_yimao.get_fushen(code, yao_index)` → static_fushen_yimao（384 条）
- 36 个普通卦：tiangan 有值，tiangan_summer/winter 为 NULL

## 7. 潜在陷阱与风险

### 规则类陷阱
- [JSON 字段处理] guaci.yao_ci 和 yong 是 MySQL JSON 类型 → Python 必须 `json.dumps(dict)` 序列化后插入，不能直接传 dict。
- [乾坤文言分隔符] 乾坤文言用 `|` 换行，不是 `\|`。前端显示时替换为 `<br>`。
- [DROP 顺序] 外键子表先于父表删除 → guali_yao 在 guali 之前 DROP。

### 数据库类陷阱
- [字符集] 卦名卦辞含中文 → 连接 URL 指定 `charset=utf8mb4`。
- [CREATE FUNCTION 重复] 用 `DROP FUNCTION IF EXISTS` 先删后建。
- [IF NOT EXISTS 建表] CREATE TABLE 没有 `IF NOT EXISTS` 语法兼容性问题 → 先 DROP 再 CREATE 确保幂等。

### 里程碑衔接陷阱
- [v0.1 回填遗漏] v0.1 完成核心算法后，容易忘记回填 static_* 数据 → 在 v0.1 第一个 Issue 中明确标注"回填 static_* 数据"。
- [v0.1 回填后不幂等] 回填使用 `INSERT` 而非 `REPLACE` → 重复执行报主键冲突。回填前应 `TRUNCATE` 或 `DELETE FROM` 三表。

### 测试盲区
- v0.0 static_* 三表为空 → 后续依赖这些表的代码（C1/C3/C4）在 v0.0 阶段无法正常查询，这是预期行为。需在文档中明确标注"v0.1 回填后可用"。
- 存储函数在空表环境下也能注册和测试——不需要表里有数据就能调用。
