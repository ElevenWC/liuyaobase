# B. 核心算法层设计文档

> 本文档详细描述核心算法层的设计，包括每个算法的输入、输出、计算规则和实现思路。
> 这些算法是整个系统的基石，被**导入模块**调用，计算结果存入预存表供查询使用。
> C1卦例显示、C3复杂检索等模块**直接查询预存表**，不调用核心算法层。

## 调用者与数据流向

### 核心算法层的定位

**核心算法层只在导入卦例时调用一次**，计算结果存入预存表。查询时直接读表，不重复计算。

## B1 时间转换算法

### 1.1 功能概述

将公历时间转换为六爻系统所需的干支时间信息。

### 1.2 输入输出

| 输入 | 类型 | 说明 |
|-----|------|------|
| `datetime` | datetime | 公历年月日时分 |

| 输出 | 类型 | 说明 |
|-----|------|------|
| `year_ganzhi` | str | 年柱（如"丙午"） |
| `month_ganzhi` | str | 月柱（如"辛卯"） |
| `day_ganzhi` | str | 日柱（如"甲子"） |
| `day_gan` | str | 日干 ← **用于计算六神** |
| `day_zhi` | str | 日支 ← **用于计算旬空、神煞** |
| `xunkong` | tuple | 旬空地支（如"辰巳"） |
| `jieqi` | str | 当前节气 |

**注意**：不需要时柱，只精确到日柱。

### 1.3 存入字段

| 计算结果 | 存入表 | 存入字段 |
|---------|--------|---------|
| 年柱 | guali_time | year_pillar |
| 年干 | guali_time | year_gan |
| 年支 | guali_time | year_zhi |
| 月柱 | guali_time | month_pillar |
| 月干 | guali_time | month_gan |
| 月支 | guali_time | month_zhi |
| 日柱 | guali_time | day_pillar |
| 日干 | guali_time | day_gan |
| 日支 | guali_time | day_zhi |
| 旬空 | guali_time | xun_kong |

### 1.4 实现方案

**使用库**：`lunar-python`

```python
from lunar_python import Solar, Lunar

def convert_time(datetime_obj):
    """公历时间转干支"""
    solar = Solar.fromDate(datetime_obj)
    lunar = solar.getLunar()

    # 获取干支
    year_ganzhi = lunar.getYearGanZhi()   # 年柱
    month_ganzhi = lunar.getMonthGanZhi() # 月柱
    day_ganzhi = lunar.getDayGanZhi()     # 日柱

    # 旬空
    xunkong = lunar.getDayXunKong()       # 返回如"辰巳"

    return {
        'year_ganzhi': year_ganzhi,
        'month_ganzhi': month_ganzhi,
        'day_ganzhi': day_ganzhi,
        'day_gan': day_ganzhi[0],
        'day_zhi': day_ganzhi[1],
        'xunkong': xunkong,
    }
```

### 1.4 节气规则 ✅ 已确认

- 节气当日即变为下月
- 例如：2026年2月4日立春，则2月4日的月支为寅
- 例如：3月5日惊蛰，则3月4日的月支还是卯（惊蛰前）

### 1.6 get_jieqi_dates 函数（C4月K聚合专用）🆕

**用途**：获取指定年份所有节气的公历日期，供C4股票关联模块进行农历月K/年K聚合。

**状态**：待新增（经审查决议C4-7）

| 输入 | 类型 | 说明 |
|-----|------|------|
| year | int | 公历年份（如 2026） |

| 输出 | 类型 | 说明 |
|-----|------|------|
| jieqi_list | list[(name, date)] | 节气名称+公历日期列表，按时间顺序，共24项 |

**示例**：

```python
def get_jieqi_dates(year: int) -> list:
    """返回指定年份的24节气日期列表"""
    from lunar_python import Solar

    jieqi_names = [
        "立春", "雨水", "惊蛰", "春分", "清明", "谷雨",
        "立夏", "小满", "芒种", "夏至", "小暑", "大暑",
        "立秋", "处暑", "白露", "秋分", "寒露", "霜降",
        "立冬", "小雪", "大雪", "冬至", "小寒", "大寒",
    ]

    result = []
    for name in jieqi_names:
        solar = Solar.fromJieQi(year, name)
        result.append((name, solar.toDate()))
    return result

# 示例：
# get_jieqi_dates(2026)
# → [("立春", date(2026,2,4)), ("雨水", date(2026,2,19)),
#    ("惊蛰", date(2026,3,5)), ...]

# C4调用者使用方式：
# 卯月 = 惊蛰当天 → 清明前一天
# 寅月 = 立春当天 → 惊蛰前一天
```

**调用者**：C4股票关联模块的月K/年K聚合服务（`KlineAggregationService`）。此函数仅返回公历日期，农历月名称（寅月、卯月...）由调用方根据节气列表自行映射。

> 节气日期通过 `lunar-python` 库获取，不自行实现节气算法。

## B2 卦象编码与纳甲装卦

1. 将卦名转换为6位二进制代码
2. 根据卦象代码为每一爻配置地支（纳甲装卦）
3. 为每一爻配置天干（可选显示）

### 2.2 卦象编码

**6位二进制代码规则**：
- 从左到右依次代表：初爻、二爻、三爻、四爻、五爻、上爻

- 外卦（上卦）：后3位（四、五、上爻）

## B4 世应伏神算法

### 4.1 世应定位

**本卦世应**：

| 宫位类型 | 世爻 | 应爻 |
|---------|-----|-----|
| 本宫卦 | 6（上爻） | 3（三爻） |
| 一世卦 | 1（初爻） | 4（四爻） |
| 二世卦 | 2（二爻） | 5（五爻） |
| 三世卦 | 3（三爻） | 6（上爻） |
| 四世卦 | 4（四爻） | 1（初爻） |
| 五世卦 | 5（五爻） | 2（二爻） |
| 游魂卦 | 4（四爻） | 1（初爻） |
| 归魂卦 | 3（三爻） | 6（上爻） |

**之卦世应** ✅ 已确认：

- 之卦世应 = 之卦本身的宫位类型 → 世应位置
- 与本卦世应使用**相同的定位表**
- 之卦世应是**之卦整体的世应**，所有6爻共享同一个世应信息

**计算步骤**：
1. 根据之卦代码（`zhi_code`）查询之卦的宫位类型
2. 根据宫位类型确定世应位置
3. 世应状态存入 `guali_yao.zhi_shi_ying`（6爻共享同一值）

### 4.2 增删伏神 ✅ 已确认

- 常驻显示
- 只显示缺失六亲的伏神

**增删伏神规则**：

| 步骤 | 操作 | 说明 |
|-----|------|------|
| 1 | 检查本卦六亲 | 统计本卦6个爻的六亲 |

### 【用户问】U2：预计算存数据库是否更快？

**用户原话**：

**【我的回答】**：

这是一个很好的问题！让我从几个方面分析：

#### 1. 哪些是"固定"的，哪些是"变化"的？

| 数据类型 | 是否固定 | 说明 |
|---------|---------|------|
| 卦象→地支 | ✅ 固定 | 乾为天的六爻地支永远是子寅辰午申戌 |
| 卦象→天干 | ⚠️ 半固定 | 乾坤的天干取决于节气，其他卦固定 |
| 卦象→六亲 | ❌ 不固定 | 六亲取决于**卦宫五行**，同一卦在不同宫的六亲不同！ |
| 卦象→六神 | ❌ 不固定 | 六亲取决于**日干**，每天都在变 |

**关键发现**：你说的"每个爻对应的六亲是固定的"其实**不完全正确**！

举例：
```
天火同人（101111）：
- 属离宫（火）时，六亲根据火来计算
- 但如果用八宫变化变成其他卦的"之卦"，情况就不同了
```

#### 2. 预计算 vs 实时计算 的对比

| 方案 | 优点 | 缺点 |
|-----|------|------|
| **预计算存数据库** | 查询快 | 存储空间大；数据不一致风险；修改逻辑需重算 |
| **实时计算** | 灵活；存储小；逻辑修改方便 | 每次都计算（但六爻计算很快） |

#### 3. 我的建议：**混合方案**

```
【存数据库】（预计算，不变或很少变）
- 64卦的纳甲地支（每个卦6个地支）
- 64卦的卦宫、宫位、五行
- 64卦的卦名、代码映射

【实时计算】（每次显示时计算）
- 六亲（取决于卦宫五行 + 爻地支五行）
- 六神（取决于日干）
- 伏神（取决于卦的六亲完整性）
- 神煞（取决于日干/日支）
- 反吟伏吟、互卦等
```

#### 4. 为什么这样设计？

1. **六亲计算非常快**：就是一个字典查找 + 简单的生克判断
2. **六神计算非常快**：就是一个查表
3. **数据一致性**：如果将来规则微调，只需改代码，不用更新数据库
4. **存储空间**：每个卦例不需要存几十个计算字段

#### 5. 性能预估

假设有1000条卦例：
- 预计算存储：每条约需30+额外字段，数据库体积增加明显
- 实时计算：每次查询耗时 < 1ms（纯内存计算）

**结论**：实时计算完全够用，不需要预计算存储。但如果将来数据量达到10万级别，可以考虑缓存策略。

#### 1. 纠正：本卦-之卦 vs 八宫变化

- **本卦-之卦**：只是记录"原来是什么卦，后来变成了什么卦"，任何爻动了都会有之卦
- **八宫变化**：是一种**解卦方法**，有特定的变化规则（一世变、二世变...归魂变）
- 两者没有直接关系，我之前混淆了，感谢纠正！

#### 2. 修正后的最终方案
