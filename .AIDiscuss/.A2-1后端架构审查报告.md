## 一、严重问题（必须补充）

### 1.1 API设计缺失

**需求来源**：.C33、.C31

**现状**：.A2第5节只有C1/C2模块的API，没有C3复杂检索模块的API。

**需要新增的API**：

```
POST   /api/search           → 执行复杂检索（核心接口）
```

**影响**：无法实现C3复杂检索模块的前后端通信。

## 二、中等问题（需要更新）

### 2.1 核心算法层与检索的关系需说明

**需求来源**：.C32、.C31

**现状**：.A2第6.2节说明核心算法层用于"实时计算动态数据"。

**问题**：根据.C31/.C32设计，C3检索模块**直接查询预存表**，不调用核心算法层。

**需要补充说明**：

| 模块 | 数据来源 | 是否调用核心算法层 |
|-----|---------|:----------------:|
| C1 卦例显示 | 预存表 + 少量实时计算 | ❌ 不调用 |
| C2 八宫变化 | 核心算法层 | ✅ 调用 |
| C3 复杂检索 | 预存表 + MySQL存储函数 | ❌ 不调用 |
| 导入模块 | 核心算法层 | ✅ 调用 |

**核心算法层的职责**：
- 只在**导入卦例时调用一次**
- 计算结果存入guali_*扩展表
- 不在查询时实时计算

## 五、我的疑问

### 【问】Q1：关系判断在哪里做？

**背景**：
- .C31提到使用MySQL存储函数
- 但也可以在Python core/层实现

**疑问**：
- 是否使用MySQL存储函数？（性能好，但维护成本高）
- 还是在Python中实现？（灵活，但需要额外查询数据）

回答:使用MySQL存储函数吧

**关于"维护成本高"的详细解释**：

| 方面 | MySQL存储函数 | Python实现 |
|------|-------------|-----------|
| 开发语言 | SQL | Python |
| IDE支持 | 有限（无智能提示、无调试） | 完善（VSCode全功能） |
| 单元测试 | 需要额外配置 | pytest原生支持 |
| 调试方式 | 只能SELECT调试，无法断点 | 可print、可断点、可查变量 |
| 修改风险 | 需连数据库DROP/CREATE，风险高 | git管理，可回滚 |
| 团队协作 | SQL文件diff可读性差 | 代码review友好 |

**降低维护成本的建议**：

1. **在core/层保留Python版本**：作为参考和单元测试用
2. **SQL文件做好注释**：每个函数写清楚逻辑和参数说明
3. **版本管理**：存储函数SQL文件纳入git管理
4. **开发流程**：先用Python验证逻辑正确性，再移植到SQL

### 【问】Q2：导入服务是否需要拆分？

**背景**：
- 当前import_service.py负责JSON导入
- 但预计算逻辑可能很复杂

**疑问**：
- 是否需要单独创建precalculate_service.py？
- 还是把预计算逻辑放在import_service.py中？

回答:单独把预计算逻辑拆分出来

### 【问】Q3：推荐方案如何存储？

**背景**：
- .C33提到"推荐方案"功能
- 用户可以保存常用的检索条件组合

**疑问**：

  - A. 内存（重启丢失）
  - B. 数据库（新建表）
  - C. 前端localStorage（不需要后端）
- 我倾向C，因为这是用户个人偏好

回答:可以只保留一个推荐方案,然后用户自己保存的方案和推荐方案都是在前端也就是C选项
